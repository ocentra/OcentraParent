# App And Game Evidence Expectations

Native app and game evidence is the product bridge between low-level process
capture and useful parent rules such as "games are limited to one hour." Browser
games are covered by managed browser URL/tab evidence. Native games and launchers
need process, window, install, launcher, and session evidence that the Rust agent
stores locally before AI, policy, or enforcement uses it.

## Outcome Bar

Parent outcome:

- A parent can see which apps, launchers, and games are installed or detectable.
- A parent can see which apps, launchers, and games are running now.
- A parent can see which app/game is foreground, how often it ran, and how long
  it has been active in the relevant time window.
- A parent can distinguish installed, running, foreground-active, background,
  unknown, and possibly-game states.
- A parent can see when a game was blocked, terminated, time-limited, or sent for
  approval, with evidence references.

Child-device outcome:

- The Rust agent observes app/game process and window evidence, writes it to the
  encrypted journal, ingests it into SQLite, and builds queryable summaries.
- The Rust agent owns sessionization, duration counts, active/foreground time,
  and enforcement handoff. AI does not scan the device.
- AI or classifier output may classify unknown evidence, but must read stored
  evidence or structured digests produced by the agent.

## Data Scope

App/game evidence may record:

- Process id, process name, executable path, parent process id where available,
  start/first-seen time, last-seen time, and observed timestamps.
- Executable publisher/signature/hash where available.
- Foreground/active-window state and window title where available.
- Installed app/game inventory from Windows install records, Start Menu
  shortcuts, known install locations, Microsoft Store/UWP package inventory, and
  launcher manifests where available.
- Launcher/library hints for Steam, Epic, Xbox, Riot, Battle.net, EA, Ubisoft,
  GOG, Roblox, Minecraft, and future supported launchers.
- Deterministic app/game catalog match, category, confidence, and unknown state.
- Session rollups: total running time, foreground time, run count, first seen,
  last seen, most recent foreground title, and evidence ids backing the rollup.

App/game evidence must not record unless a later milestone explicitly approves
it:

- Screen contents or screenshots.
- Keystrokes, chat content, voice content, or game telemetry payloads.
- Decrypted network traffic.
- Private launcher account tokens or credentials.

## Trust Boundary

- Native process/window adapters observe OS state and return adapter
  observations.
- Installer, shortcut, package, and launcher-manifest adapters observe local
  metadata but do not call AI directly.
- The Rust agent writes raw observations and derived session summaries to local
  journal/query storage before policy, AI, or enforcement consumes them.
- AI consumes evidence references or structured digest files generated by the
  agent. AI output is classification or decision support, not source truth.
- Portal views display app/game evidence and policy outcomes, but do not scan the
  OS, classify processes, run timers, or enforce.

## Expected Deliverables

- Installed app/game inventory contract.
- Running process observation contract with path/signature/hash fields where
  available.
- Foreground app/game session contract.
- Launcher manifest adapter contract for supported launchers.
- Deterministic app/game catalog match and unknown-game state.
- Session summary contract with running time, foreground time, run count,
  first/last seen, and evidence references.
- AI digest/input contract that references stored app/game evidence instead of
  scanning the machine.
- Policy target contract for app, process, launcher, category, and game title.
- Enforcement handoff contract for block, terminate, time-limit, and ask-parent.

## Runtime Flow

```text
process/window/install/launcher observations
  -> encrypted journal
  -> SQLite query store
  -> app/game session summary
  -> optional AI/classifier digest for unknown or ambiguous apps
  -> deterministic policy evaluator
  -> enforcement adapter or permission request
  -> auditable parent-visible result
```

The common game-control path should be:

1. Rust agent observes that a game process is running.
2. Rust agent stores the process/window evidence and updates the app/game session
   summary.
3. Rust agent or deterministic catalog marks it as game evidence where known.
4. AI may classify only unknown or ambiguous evidence from the stored digest.
5. Policy evaluator checks parent game/category/time-budget rules.
6. If the rule says the game is over the limit or blocked, the enforcement
   adapter terminates or blocks the target.
7. Child-facing status explains that the app/game was stopped by parent policy
   and asks the child to request permission from the parent.
8. Parent portal shows the evidence, duration, rule, action, and result.

## Acceptance

- The system can distinguish "Steam is running" from "a Steam game is running"
  when launcher/library/process evidence makes that distinction possible.
- Known games can be matched deterministically before AI is used.
- Unknown or ambiguous processes remain unknown or ask-parent until there is
  enough evidence to classify safely.
- Session summaries report running time and foreground time from stored evidence,
  not from portal state.
- AI input references stored app/game evidence and summaries; AI cannot scan the
  OS or invent duration.
- A parent game/category time-limit policy can consume a session summary and
  produce a dry-run decision before enforcement is enabled.
- Source freshness readiness must gate policy preview output: stale, missing,
  manual-required, unavailable, or not-claimed inventory/runtime/foreground/
  launcher source rows cannot become preview-ready policy rows.
- Source-gated policy preview read models must derive from source freshness
  preview-gate rows, expose redacted evidence refs rather than raw private
  source rows, and keep source-manual-required rows separate from
  compiler-manual-required rows before any service runtime or portal renderer
  claims exist.
- Category, risk, and game-context candidates can route into parent policy
  compiler targets only when active category proof, confidence/source
  disclosure, and supporting evidence refs exist; local-AI routes cite digest
  refs, manual-review routes stay manual-required, and no category/risk route
  dispatches an adapter.
- Policy readiness consumes only service-backed app/game `sourceStatusRows`.
  Native app policy compile requires fresh inventory, runtime, and foreground
  evidence; native game policy compile also requires fresh launcher evidence.
  Stale, missing, permission-limited, unavailable, adapter-error,
  manual-required, and not-claimed rows block policy compile without exposing
  raw private source rows or calling adapters.
- Enforcement, when enabled, records whether the game/app was terminated, already
  exited, unavailable, blocked, or left running in observe-only mode.

## Done Signal

A local run records real app/game process evidence into the journal and query
store, derives a queryable app/game session summary with duration, feeds only
that stored evidence or digest into AI/policy, and can produce a parent-visible
dry-run or enforcement handoff for a game time-limit rule without pretending AI
scanned the machine.
