## Current Refresh Audit - 2026-06-19
- Boundary snapshot: `packages/billing-domain/package.json` exposes `./*` from `dist/src/*.js`, and the package tree under `packages/billing-domain/src` is still a dense mix of billing contracts, proof/read-model files, and support-admin surfaces rather than a narrow domain core.
- Responsibility fit: the package still fits billing contract ownership, but it now carries several adjacent proof/reporting concerns. `packages/billing-domain/src/package-info.ts` is a thin identity shim, and `packages/billing-domain/tests/unit/package-info.test.ts` only proves that identity.
- DRY hotspots:
  - `packages/billing-domain/src/billing-entitlement.ts` and `packages/billing-domain/src/billing-support-admin-boundary.ts` both define nearly identical failure-state schemas and filters around `retainEvidenceExportAccess` and `existingLocalSafetyContinues`.
  - `packages/billing-domain/src/billing-entitlement-values.ts` and `packages/billing-domain/src/billing-support-admin-boundary-values.ts` repeat the same small claim vocabulary (`not-implemented`, `not-executed`, `not-included`) instead of centralizing those literals.
  - `packages/billing-domain/src/billing-support-admin-status-proof.ts`, `packages/billing-domain/src/billing-entitlement-runtime-proof.ts`, and `packages/billing-domain/src/billing-account-runtime-boundary.ts` all carry proof/read-model narration or known-gap style metadata alongside schema logic, which makes the package harder to decompose cleanly.
- Barrel / shim debt: no TS or Rust barrel files or re-export shims were found in `packages/billing-domain/src`. The only package-level indirection is the wildcard export in `packages/billing-domain/package.json`; `src/package-info.ts` is just a thin identity shim.
- Schema / proof drift risk: the support-admin surface is split across `billing-support-admin-boundary.ts`, `billing-support-admin-boundary-values.ts`, and `billing-support-admin-status-proof.ts`, while entitlement uses `billing-entitlement.ts`, `billing-entitlement-values.ts`, and `billing-entitlement-runtime-proof.ts`. That is workable today, but the same failure and claim semantics are duplicated enough that drift is likely if any one file changes first.
- Event / log / proof misuse: none observed in the inspected boundary. There is no event-bus layer here, and the proof rows are explicitly modeling non-claims and redaction-safe refs rather than runtime logging.
- Test / proof structure issues: the package leans on source-level proof builders and unit tests instead of a clearer contract-vs-proof split. The current shape is acceptable, but it pushes correctness pressure onto schema filters and makes the proof layer harder to reuse.
- DRY score: 64/100. Shared schema reuse is real, but the billing failure-state and proof/reporting clusters still carry enough repetition to justify a cleanup slice.
- Fix recommendation: centralize the repeated billing failure-state and claim-literal schemas into one shared billing proof/core module, then keep canonical contract types separate from proof/read-model narration.
- Decouple recommendation: split along surface boundaries, not by file count. The most likely paths are `packages/billing-domain/src/billing-entitlement*.ts` for canonical entitlement contracts, `packages/billing-domain/src/billing-support-admin*.ts` for support-admin proof/reporting, and a smaller shared values module for the repeated claim literals and failure-state primitives.
- Blockers: none for audit reporting. The package is just dense enough that any cleanup should be handled in a follow-up slice rather than inside this refresh note.
