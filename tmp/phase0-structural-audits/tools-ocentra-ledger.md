## Current Refresh Audit - 2026-06-19
- Responsibility: `tools/ocentra-ledger` owns the ledger tool surface end to end, including domain schemas, append-only events, materialization, CLI commands, daemon startup, HTTP peer/server routes, local sync, retention/compaction, doctor/guard/notify utilities, and the package-local test harness.
- Dependencies: Effect Schema, Node standard library modules, `fetch`/HTTP primitives, and the package's own `domain.ts`, `events.ts`, `materialize.ts`, `paths.ts`, `stream.ts`, `identity.ts`, `doctor.ts`, `guard.ts`, `notify.ts`, `retention.ts`, `server.ts`, and sync modules.
- Violations: No major ownership breach or external product leakage is visible; the structural problem is internal duplication, with command parsing and validation repeated across the CLI and HTTP server, plus a broad top-level CLI that owns too many unrelated concerns.
- Duplicated shapes: `cli.ts` and `server.ts` both encode the same command families and argument/body validation; `materialize.ts` and `notify.ts` both adapt materialized state into lane/worker-facing shapes; `sync/http.ts` and `sync/local.ts` duplicate prefix-check, line-splitting, and conflict-copy logic; `domain.ts` keeps several closely related identity/state literal families that are easy to drift.
- Barrel/re-export/shim debt: No barrel or re-export chain was found in the package source, which is good; the remaining debt is a thin launch shim in `daemon.ts` plus the CLI/server command mirrors, not export shims.
- Schema drift: `domain.ts` and `events.ts` are coherent, but the hand-rolled request parsing in `server.ts` and the command switch in `cli.ts` can drift from the central schemas because the same command fields and state names are validated in multiple places.
- Event/log/proof misuse: The package is event-ledger oriented and does not show raw logging abuse in the source reviewed, but proof is mostly implicit in tests and diagnostics rather than emitted as a structured, reusable proof chain for CLI, server, daemon, and sync operations.
- Test/proof structure issues: `materialize.test.ts` is a single 839-line catch-all suite that mixes domain, sync, HTTP, daemon, CLI, retention, doctor, and guard coverage; that gives broad coverage, but it hides ownership boundaries and makes isolated proof failures harder to read and maintain.
- DRY score 0-100: 63/100. Reasons: strong single-source domain/event schema ownership and append-only ledger semantics; moderate duplication in command routing, request parsing, and sync conflict handling; large god-file pressure in `cli.ts` and `materialize.ts`; and test coverage concentrated in one very large suite rather than split by boundary.
- Fix recommendation: Extract a shared command specification or handler map for the CLI and HTTP server, then split `cli.ts` by command family so routing, append logic, and daemon/bootstrap concerns do not live in one file.
- Decouple recommendation: Separate package-local concerns into explicit ownership slices such as command routing, HTTP peer/server plumbing, projection/materialization, sync adapters, and proof/diagnostic helpers so each layer can be changed without touching the others.
- Blockers: None for this refresh append; no implementation work is requested, and the audit is based on the current source snapshot only.
