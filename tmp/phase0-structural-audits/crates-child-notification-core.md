## Current Refresh Audit - 2026-06-19

- Responsibility: child-side parent notification shaping. `tracking_notification.rs` turns tracking policy violations into parent notification requests; `child_domain_notification.rs` forwards child-domain notification requests; `policy_control_notification.rs` shapes policy-request + delivery state into parent-visible notification records.
- Deps: `ocentra-eventing`, `ocentra-parent-agent-protocol`, `ocentra-policy-control-core`, `serde`. The dependency set is fine for a shaping crate, but it also pulls in validation helpers from policy control, so the boundary is already partly coupled to upstream contract ownership.
- Violations: no forbidden Rust `pub use` re-export exists, but `src/lib.rs` is still a thin module frontage shim that exposes every submodule at the crate root; the main structural debt is the mixed responsibility inside `policy_control_notification.rs`, not an actual re-export barrel.
- Duplicated shapes: `tracking_notification.rs` and `child_domain_notification.rs` are both one-line passthrough adapters; `policy_control_notification.rs` repeats request-status-to-notification-state mapping, override shape checks, delivery matching, and audit-ref dedupe in one file.
- Barrel/reexport/shim debt: `crates/child-notification-core/src/lib.rs` is a frontage shim, and the two forwarding modules are shim layers with no local logic. They are small, but they keep the crate split into more files than the ownership boundary needs.
- Schema drift: `PolicyControlNotificationState` is broader than the request/delivery shapes it derives from, so future additions in `ocentra-policy-control-core` can drift unless the mapping stays in lockstep. The state mapping for `delivery-*` versus request states is especially sensitive.
- Event/log/proof misuse: the crate correctly stays log-free, but it is being used as contract-shaping proof surface without any populated proof artifacts. `crates/child-notification-core/proof/` and `crates/child-notification-core/proofs/{ci,local}/` are empty except keep files, so there is no durable proof chain for the notification contract beyond unit tests.
- Test/proof structure issues: tests are all local unit tests under `crates/child-notification-core/tests/unit/*.rs`; there is no crate-level proof summary, no CI/local proof artifact, and no negative cross-crate proof that exercises the formatter against future upstream state growth.
- Score: 72/100, high risk. The crate is small and coherent at runtime, but the contract boundary is still too fanned out for such a thin adapter layer.
- Fix recommendation: collapse the pure forwarding modules into the owning protocol helpers or make them explicit adapter modules with a single purpose; then split policy-control notification shaping from validation/dedupe if additional consumers appear.
- Decouple recommendation: move the request/delivery validation and audit-ref merge logic closer to `ocentra-policy-control-core`, leaving this crate to assemble the parent-facing notification record and channel-specific request objects only.
- Blockers: no audit-refresh blocker. A real refactor would need coordinated updates in the upstream contract owners if notification states, delivery states, or audit-reference rules change.
- Exact likely paths: `crates/child-notification-core/src/lib.rs`; `crates/child-notification-core/src/tracking_notification.rs`; `crates/child-notification-core/src/child_domain_notification.rs`; `crates/child-notification-core/src/policy_control_notification.rs`; `crates/child-notification-core/tests/unit.rs`; `crates/child-notification-core/tests/unit/tracking_notification.rs`; `crates/child-notification-core/tests/unit/child_domain_notification.rs`; `crates/child-notification-core/tests/unit/policy_control_notification.rs`; `crates/child-notification-core/proof/`; `crates/child-notification-core/proofs/local/`; `crates/child-notification-core/proofs/ci/`.
