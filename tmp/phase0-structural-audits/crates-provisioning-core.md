## Current Refresh Audit - 2026-06-19

- Responsibility: still a provisioning/readiness projection crate, but the live surface is broader than the package name suggests because `src/provisioning_install.rs` owns readiness evaluation, family-context projection, event creation, idempotency shaping, and recovery/action derivation in one module.
- Deps: current direct deps stay narrow (`ocentra-family-identity-core`, `ocentra-eventing`, `serde`, `serde_json` for tests), but the family-identity dependency is carrying most of the canonical setup/provisioning semantics instead of a thin adapter boundary.
- Violations: ownership is still split across provisioning-core and `packages/setup-domain`; the Rust crate directly imports household/session/setup recovery evaluators instead of being a pure projection facade, so the canonical setup lifecycle is not cleanly separated.
- Duplicated shapes: `AccountReadinessState`, `ParentAppReadinessState`, `ChildInstallState`, `ChildServiceState`, `ChildAppReadinessState`, `PermissionReadinessState`, `PairingLifecycleState`, `PolicyBaselineState`, `DataCustodySyncState`, `NetworkReachabilityState`, and the readiness/blocker/action triplets all mirror the TS setup-domain state machine shapes.
- Barrel/reexport/shim debt: there is no forbidden `pub use` barrel in the crate, but `crates/provisioning-core/src/lib.rs` is only a thin module fan-out and `provisioning_install.rs` acts as a large shim/coordinator layer with many `*_from_family_context` and `provisioning_*` wrapper functions instead of a smaller boundary.
- Schema drift: Rust owns extra intermediate states that do not line up 1:1 with the TS setup-domain schemas, especially around child app/service readiness and recovery projection, so the same lifecycle is represented by different shape vocabularies on each side.
- Event/log/proof misuse: the crate emits typed domain events and has payload-shape assertions, but there is still no logger-ready proof chain in the crate surface and the tests mostly prove serialization/decision shape rather than a correlated chain from input to event to downstream consumption.
- Test/proof structure issues: `tests/unit/readiness.rs` and `tests/unit/readiness_flow.rs` combine many scenarios in file-local fixture blocks, which keeps the coverage useful but makes the proof structure hard to slice by responsibility or by contract vs projection behavior.
- Score: 3/10; structurally functional, but still high-overlap and high-drift relative to the canonical setup/readiness surface.
- Fix recommendation: pick one canonical owner for the setup/provisioning lifecycle taxonomy, then make the other side a projection-only adapter with a much smaller enum/input surface and narrower event-shaping responsibility.
- Decouple recommendation: move the shared lifecycle taxonomy into one owner and leave provisioning-core responsible only for readiness evaluation plus event projection; keep family-identity-core as the source of authorizations/recovery facts, not a second lifecycle state machine.
- Blockers: no audit-writing blocker remains; the remediation blocker is the unresolved product ownership decision between provisioning-core, setup-domain, and family-identity-core.
- Exact likely paths: `crates/provisioning-core/src/lib.rs`; `crates/provisioning-core/src/provisioning_install.rs`; `crates/provisioning-core/tests/unit.rs`; `crates/provisioning-core/tests/unit/readiness.rs`; `crates/provisioning-core/tests/unit/readiness_flow.rs`; `packages/setup-domain/src/readiness.ts`; `packages/setup-domain/src/setup-state-machine.ts`; `packages/setup-domain/src/pairing-intent.ts`; `packages/setup-domain/src/family-setup-bridge.ts`; `crates/family-identity-core/src/setup_lifecycle.rs`; `crates/family-identity-core/src/session_lifecycle.rs`; `crates/family-identity-core/src/household_authority.rs`.
