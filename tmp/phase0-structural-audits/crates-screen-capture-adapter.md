## Current Refresh Audit - 2026-06-19

- responsibility: Low-level screen capture adapter for active-window, selected-window, and primary-display screenshots, plus capture metadata and a trigger-to-schedule mapping layer.
- dependencies: `ocentra-parent-agent-protocol` is directly used by `src/lib.rs` and `src/trigger_scheduler.rs`; `xcap` is the desktop capture backend in `src/desktop_xcap.rs`; `linux_x11.rs` shells out to `xprop`, `xwininfo`, `xwd`, `convert`, and `identify`; `base64`, `sha2`, and `serde_json` are declared in `Cargo.toml` but did not surface in the inspected source files.
- violations: `src/trigger_scheduler.rs` keeps proof-label and suppression-label routing inside the adapter boundary instead of a higher screen runtime/policy layer; `pub mod trigger_scheduler` exposes that policy edge from the crate root; `src/linux_x11.rs` embeds platform command orchestration directly in the adapter rather than behind a narrower OS helper boundary.
- duplicated_shapes: `src/lib.rs`, `src/desktop_xcap.rs`, and `src/linux_x11.rs` all repeat the same degrade-or-capture flow with near-identical metadata assembly; the selected-window and active-window branches are structurally similar in both backends; scheduler trigger mapping is a table-driven mirror of protocol constants.
- barrel_reexport_shim_debt: No TS/JS barrels or Rust `pub use` re-exports were observed in the inspected files; the remaining shim-like debt is policy placement, not export shape.
- schema_drift: The public capture metadata shape is coherent, but the scheduler vocabulary is still anchored to protocol proof-label constants rather than a crate-local capture schema; `ScreenCaptureWindowTitleQuery` is a narrow owned wrapper and does not currently show drift.
- event_log_proof_misuse: No runtime logging or event-bus misuse was present in the inspected files; the only proof-adjacent coupling is the scheduler mapping against protocol constants, which keeps proof semantics too close to the adapter.
- test_proof_structure_issues: Tests cover the query wrapper and scheduler decisions, but they do not exercise platform capture fallback paths, metadata shape stability, or redaction boundaries; `tests/unit.rs` is only a module loader, so the crate’s proof structure is thin for the actual capture backends.
- dry_score_0_to_100: 33. The adapter owns the right low-level capture work, but policy mapping is still mixed in, backend plumbing is duplicated, and the current tests do not validate the real capture/degradation seams.
- dry_score_reasons: Ownership is mostly coherent but not tight; dependency direction is acceptable for the platform backends but weaker for `trigger_scheduler.rs`; shared capture plumbing is repeated across desktop and X11 implementations; proof coverage is shallow relative to the adapter’s boundary.
- fix_recommendation: Move trigger-to-schedule mapping out of the adapter crate or isolate it into a clearly named policy mapper owned by the screen runtime layer; keep the adapter focused on capture mechanics and metadata production only.
- decouple_recommendation: Extract a shared capture-result builder or backend helper so `desktop_xcap.rs`, `linux_x11.rs`, and `src/lib.rs` stop duplicating degrade/capture assembly; keep protocol-label mapping and suppression decisions outside the adapter.
- blockers: No direct blocker for audit refresh; the only open question is whether the scheduler mapping is intentionally parked here for compatibility, which would need a higher-layer owner decision before refactoring.
