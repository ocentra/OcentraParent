## Current Refresh Audit - 2026-06-19

- responsibility: `crates/agent-updater` owns installed-agent updater and maintenance tooling, including signed manifest verification, update selection, artifact hashing, network fetch/download, and MSI launch.
- dependencies: the crate pulls in `reqwest`, `tokio`, `semver`, `base64`, `ed25519-dalek`, `sha2`, `serde`, `serde_json`, `rand_core`, and `tempfile`, so transport, crypto, parsing, and process orchestration all sit in one runtime boundary.
- violations: the boundary is still broad for a single owner slice because `manifest.rs` signs and verifies, `update.rs` decides the update flow, `network.rs` fetches artifacts, `hash.rs` verifies integrity, and `installer.rs` launches `msiexec.exe`.
- duplicated shapes: `UpdateManifestPayload` and nested manifest structs are repeated as runtime contract shapes and as test fixtures; `tests/manifest_contract.rs` and `tests/contract/manifest_policy.rs` both rebuild the same manifest payload shape; `src/bin/updater.rs` and `src/bin/tool.rs` are thin frontends over the same core.
- barrel/re-export/shim debt: there are no observed Rust re-export barrels, but there is shim debt in `src/bin/updater.rs`, `src/bin/tool.rs`, and `src/lib.rs` because the public surface is mostly frontage over deeper runtime helpers instead of a clearer owner split.
- schema drift: manifest schema lives inside the runtime crate rather than a separate shared schema package, so the `camelCase` JSON contract, the policy checks, and the contract tests are all coupled to the same module set and can drift together without a dedicated schema boundary.
- event/log/proof misuse: the updater flow is imperative and uses direct process/stdio-style control instead of a structured log or event boundary; `eprintln!` at the binary edge is not a proof chain, and there is no explicit event/read-model seam for update decisions.
- test/proof structure issues: `tests/contract.rs` is only a path shim into `tests/contract/manifest_policy.rs`; the manifest contract coverage is split between two test files that mirror the same payload shape, which makes the proof surface harder to reason about than a single manifest-contract owner would.
- dry_score_0_to_100: 41
- dry_score_reason: the score stays low because one crate owns signing, verification, transport, hashing, installer launch, and CLI frontage; the manifest contract is duplicated in tests; the runtime boundary is wider than the owned updater lifecycle; and the only meaningful decoupling is still inside helper modules rather than in separate owner packages.
- fix_recommendation: split the crate into a manifest-contract owner, an update-runtime owner, and a maintenance-tool owner, or at minimum factor those responsibilities into explicitly owned submodules with a smaller public surface and structured output.
- decouple_recommendation: move shared manifest/schema shape and policy into a contract-focused package, keep execution/update/install concerns in a runtime package, and isolate tooling/signing paths so the updater binary no longer carries manifest-authoring and installer-launch responsibilities together.
- blockers: none for this audit refresh; the only limitation is that this is still a documentation-only refresh and not a structural refactor.
