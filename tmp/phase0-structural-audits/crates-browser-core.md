## Current Refresh Audit - 2026-06-19
- responsibility: `crates/browser-core` owns browser runtime observation intent mapping, observed-event synthesis, evidence/request fan-out, and browser performance-budget evaluation. The crate is still a thin facade over two small modules plus crate-root helpers, not a broader browser domain owner.
- dependencies: live dependencies are `ocentra-eventing`, `ocentra-parent-agent-protocol`, `ocentra-evidence` (used by browser-flow tests), and `serde`. Direct protocol imports are expected for the child-domain event chain; no extra transport layer is present.
- violations: no current barrel/re-export violation was observed in this snapshot. The previous `pub use` audit note is stale. The remaining design tension is that the crate root still centralizes helper forwarding and decision mapping in one frontage.
- duplicated shapes: `BrowserRuntimeInput`, `BrowserRuntimeDecision`, and the browser intent/action/hand-off enums mirror the `network-core` runtime pattern closely. The `browser_text_id!` macro repeats a generic string-validation wrapper shape that could live in a shared helper.
- barrel/re-export/shim debt: no active barrel debt in `src/lib.rs`, but the crate root is still a shim-like boundary that forwards to `runtime_decision` and `performance_budget` while also owning browser observation helpers. That is thin-frontage debt, not a re-export violation.
- schema drift: low current drift risk. The browser child-domain event chain still aligns with the protocol crate, and the tests confirm observation, evidence, AI request, and policy request behavior. The main drift risk is localized string-id and event-chain duplication, not field mismatch.
- event/log/proof misuse: no runtime logging or proof-chain misuse was observed in the target files. The gap is absence, not incorrect usage: this crate participates in an event/evidence/request chain but does not emit structured redacted proof milestones or logger-ready breadcrumbs of its own.
- test/proof structure issues: tests are split cleanly by behavior, but they are all unit-level and mostly mirror the branch table. There is no dedicated architecture/proof gate around the crate root, and the performance tests only validate the canned fixture matrix rather than a broader proof chain or ingest path.
- DRY score 0-100 with reasons: 63/100. The crate is small and well-scoped, but it duplicates the browser/network runtime decision shape, repeats local string-id validation, and keeps helper ownership split across crate root and module files. The score is not lower because the current snapshot removed the earlier re-export barrel and the test coverage is behaviorally coherent.
- fix recommendation: extract a shared child-runtime decision/event-chain helper for browser and network, move the generic string-id wrapper into a common runtime helper, and keep browser-specific mapping in module-local APIs. Add a focused architecture check on `crates/browser-core` so the root stays a boundary instead of becoming a frontage again.
- decouple recommendation: separate decision policy, event-chain synthesis, and performance-budget data/evaluation into clearer ownership units. If this crate grows, split the root helper surface from the module implementations so browser-specific logic does not accumulate in `src/lib.rs`.
- blockers: no blocker for the audit refresh itself. Remediation is blocked only on choosing the shared-helper owner crate and on whether the network/browser duplication should be collapsed together or in staged passes.
