## Current Refresh Audit - 2026-06-19
- responsibility: `apps/portal` is the Vite portal shell for local/LAN parent visibility, WebSocket transport, and route orchestration. `apps/portal/README.md` and `apps/portal/src/main.ts` make it clear this package is the browser-facing shell, not the source of truth for child-device capture, policy execution, or enforcement.
- dependencies: The shell depends on `@ocentra-parent/agent-protocol-domain`, `@ocentra-parent/portal-domain`, `@ocentra-parent/logging-domain`, React, Vite, and local portal helpers. The dependency shape in `apps/portal/package.json` is appropriate for a UI shell, but `apps/portal/src/PortalApp.tsx` and `apps/portal/src/ParentPortalRoute.tsx` also pull in a large number of route panels and vendored UI surface helpers, which makes the app layer carry more route-specific coordination than a thin shell should.
- boundary_violations: The main recurring boundary issue is local re-derivation of shared route logic. `apps/portal/src/main.ts` parses and normalizes the hash route locally before falling back to `PortalRoute.Overview`, `apps/portal/src/PortalApp.tsx` duplicates the notion of dev protocol route grouping, and `apps/portal/src/ParentPortalRoute.tsx` contains additional browser-hash branching for social-panel selection. These are shell-level copies of contract/domain concerns and should stay on the domain side.
- duplicated_shapes: `getRoute` in `apps/portal/src/main.ts` overlaps with `PortalRouteSchema` and `PortalRoutes` from `@ocentra-parent/portal-domain/contracts`; `isPortalDevProtocolRoute` in `apps/portal/src/PortalApp.tsx` hardcodes the same route grouping already expressed by the domain route set; `renderRouteContent` in `apps/portal/src/portal-route-content.ts` is a thin route switch over only `Commands`, `Events`, and `Logs`. The result is several small shims that duplicate shared route semantics instead of composing them.
- barrel_reexport_shim_debt: No barrel or re-export violations were found in the inspected `apps/portal` files. The narrow grep over `apps/portal` did not surface any `export *`, `export { ... } from`, or Rust-style `pub use` patterns. The remaining shim debt is structural, not export-shape debt: `renderRouteContent`, `isPortalDevProtocolRoute`, and `resolveBrowserPanelEvent` are all thin forwarding/branching helpers that make the shell wider without adding new ownership.
- schema_drift: `apps/portal/src/PortalApp.tsx` still contains app-local route classification and route-state gating that can drift from `portal-domain` contract changes. `apps/portal/src/ParentPortalRoute.tsx` also derives browser panel selection from both hash contents and selected events, which increases the chance that displayed route intent can diverge from the contract-defined route descriptors.
- event_log_proof_misuse: `apps/portal/src/dev-logger.ts` shows strong proof-trace support, but it also mixes bridge delivery, compatibility logging, and proof-trace shaping in one module. That is acceptable for the shell, yet it is a place where log/proof semantics can become too broad if future changes start treating these logs as product evidence instead of dev/proof transport. `apps/portal/src/main.ts` correctly writes the portal-started log and `apps/portal/src/PortalApp.tsx` keeps event-driven UI state local, so there is no obvious misuse of event logs as product state.
- test_proof_structure_issues: `apps/portal/package.json` exposes `test:e2e`, `test`, and `lint:exec`, but the audit surface suggests the proof model is still concentrated in the runtime shell and in a single Playwright runner path rather than being decomposed by route or behavior family. `apps/portal/README.md` documents the browser proof flow, but the app layer itself still owns route parsing and route switching, which makes proof failures harder to isolate to a single contract boundary.
- responsibility_fit: The package correctly owns browser shell rendering, transport, and UI orchestration. It should not own route normalization, route-group classification, or contract-like branching rules. `apps/portal/src/PortalApp.tsx` is the clearest place where the shell begins to look like a policy router instead of a thin host.

- fix_recommendation: Move route normalization and route-group classification fully into `@ocentra-parent/portal-domain` helpers, then keep `apps/portal` as a renderer/dispatcher that only consumes those helpers. The best first slice is `apps/portal/src/main.ts` plus the route-selection helpers in `apps/portal/src/PortalApp.tsx` and `apps/portal/src/ParentPortalRoute.tsx`.
- decouple_recommendation: Extract a single shared route descriptor and route-family source of truth, then make `renderRouteContent` a pure consumer of that source instead of a parallel router. This would reduce drift and make the portal shell easier to test in isolation.
- blockers: No blocking source defect was verified in this refresh. The only blocker is that the app still depends on contract-side route ownership being correct and stable; if the domain route set changes, the shell’s local copies are the first likely drift points.
