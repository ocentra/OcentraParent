## Current Refresh Audit - 2026-06-19
- responsibility: Owns storage custody decisions and event projection for retention, export, remote upload, tombstone, and audit markers. In practice the module also carries remote-sync and parent-export semantics, so its responsibility boundary still overlaps the broader custody domain.
- dependencies: Only `ocentra-eventing` and `serde` in the manifest. Dependency shape is lean; the risk is not external bloat but semantic duplication across crates.
- violations: The crate repeats custody vocabulary that appears to belong in the TS data-custody owner, and `lib.rs` is a blanket re-export shim instead of a narrow surface. That makes ownership look flatter than it really is.
- duplicated shapes: `StorageCustodyLocation`, `RetentionWindowState`, `ParentExportState`, `RemoteSyncState`, `LocalPayloadRetentionAction`, `ParentExportPacketState`, `RemoteUploadState`, `StorageTombstoneState`, and `StorageAuditState` mirror the same decision axes already represented in the data-custody domain.
- barrel/re-export/shim debt: `crates/storage-custody-core/src/lib.rs` is only `mod storage_custody;` plus `pub use storage_custody::*;`. That is a classic shim that hides the real module boundary and makes future splits harder.
- schema drift: `StorageCustodyInput` and the event helpers hard-code the current policy contract in Rust, while the matching TS custody vocabulary is already described elsewhere. The likely drift point is the shared meaning of retention/export/remote-upload states, not the primitive event types themselves.
- event/log/proof misuse: Event contracts and idempotency keys are built inline in `src/storage_custody.rs`, but the crate does not separate pure custody policy from event projection. There is no runtime logging here, so the concern is proof-shape drift: event creation is coupled directly to decision logic and will be harder to validate independently.
- test/proof structure issues: The tests split the same scenario family across `tests/unit/custody_decision.rs` and `tests/unit/custody_flow.rs`, with overlapping arrange/act/assert shapes for expired retention, parent export, remote upload gating, and action-plan projection. Coverage is decent, but the proof structure is duplicated instead of table-driven or scenario-shared.
- dry_score: 61/100. The core logic is compact and dependency-light, but the crate still mixes policy, event projection, and naming ownership in one module tree, with a re-export shim and duplicated scenario shapes lowering DRY value.
- fix_recommendation: Keep one owner for custody vocabulary, then narrow this crate to the storage-specific decision core and explicit event helpers. Replace the blanket lib re-export with a smaller exported surface once the ownership split is settled.
- decouple_recommendation: Split pure custody policy from event/materialization concerns first, then move any shared retention/export/remote-upload vocabulary into the single domain owner. If the TS data-custody package is the real owner, this crate should consume that shape instead of shadowing it.
- blockers: No local build blocker is visible from this read. The real blocker is cross-crate ownership: until the shared custody vocabulary owner is chosen, every cleanup here risks moving the duplication rather than removing it.
